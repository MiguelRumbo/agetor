# Traducción de la UI (español)

Subsistema del fork: `src/mainview/lib/i18n/`. Contrato:

- **Inglés por defecto.** `t("texto en inglés")` devuelve la traducción de `es.ts` si el idioma es `es`, y el mismo texto si no hay entrada. Así los tests unitarios y los e2e, que buscan texto en inglés, no cambian.
- **La clave es el texto inglés exacto.** Si se edita un texto en un componente hay que editar la clave en `es.ts` (si no, esa cadena vuelve a verse en inglés, sin romper nada).
- **Marcadores `{nombre}`**: `t("Hello {name}", { name })`. `index.test.ts` comprueba que cada traducción conserva los mismos marcadores.
- **Idioma en `localStorage`** (`agetor:locale`), leído de forma síncrona al cargar el módulo. Cambiarlo con el selector de **Ajustes → General → Idioma** recarga la página, porque `t()` también se evalúa en constantes de módulo.
- **Columnas del tablero**: `tColumn(label)` con `esColumns` (aparte porque "Review" también es un verbo en otros sitios).
- **Modos y esfuerzos** de `AGENT_OPTIONS` se traducen al mostrarlos (`t(m.label)`); los `id` no se tocan. Los `hint` largos siguen en inglés.
- Si un archivo ya tiene una variable local `t` (p. ej. `(t) => t.id`), se importa como `import { t as tr }` y se llama `tr("…")`: `App.tsx`, `SettingsDialog.tsx`, `TerminalView.tsx`.

## Cómo añadir una cadena

1. Envolver el texto en el componente con `t("…")`.
2. Añadir `"…": "…"` a `es.ts`.
3. `bun test src/mainview/lib/i18n`.

## Core y CLI

Un solo idioma para toda la app: la preferencia `locale` (`en`/`es`) de la tabla `preferences`. El selector de Ajustes la guarda (además de `localStorage`); al arrancar, la UI se alinea con ella si otro cliente la cambió.

- **Traductor compartido** `src/shared/i18n-core.ts`: la clave es el texto inglés; si lleva `{marcadores}` es una plantilla que se compara con el mensaje ya interpolado (`"task {id} not found"` ↔ `task abc not found`). Así el core traduce errores dinámicos sin tocar cada sitio.
- **Core** (`src/bun/i18n.ts`, diccionario `i18n-es.ts`): `json()` de `server.ts` traduce el campo `error` de toda respuesta (único punto de paso); `saveAndEmit` de `orchestrator.ts` traduce las líneas de estado al escribirlas. El evento se guarda ya traducido: un estado antiguo no cambia al cambiar de idioma. Solo hay entradas para lo que ve una persona; el resto sale en inglés.
- **No traducir** lo que el cliente compara por texto: `TMUX_MISSING_REASON`, `IMPORT_FAILED_PREFIX`, `"task is bound to agent …"` (CLI), mensajes con `Settings → …` (`credential-error.ts`) ni ningún `*_PREFIX` de estado. Los errores de herramientas externas (git, tmux, el CLI del agente) tampoco.
- **CLI/TUI** (`src/cli/i18n.ts`, diccionario `i18n-es.ts`): idioma por `AGETOR_LANG` (`en`/`es`), si no por la preferencia `locale` de un core ya en marcha (nunca arranca uno solo para leerla), si no inglés. Dos tipos de clave: frase completa y **fragmento de plantilla** (el texto fijo entre `${…}`, p. ej. `"created harness"` en `` `${c.green("✓")} created harness ${c.bold(id)}` ``), de modo que colores y valores no se tocan. `ctHelp()` traduce `--help` línea a línea (descripción tras el hueco de 2+ espacios).
- Los nombres de subcomandos y flags no se traducen.

## Qué queda en inglés (pendiente)

- La prosa larga de `agetor <cmd> --help` (solo se traducen la ayuda principal y los resúmenes de una línea).
- Salida del CLI que se compone con variables sin pasar por `out(\`…\`)` (p. ej. `out(texto)` ya armado), etiquetas de `agetor show`, y errores del core que no están en el diccionario.
- Errores técnicos de validación del core (nombres de campos del cuerpo JSON) y los de herramientas externas.
- Frases con ternarias o plantillas `${}` en la UI que el volcado automático no capturó, y los `hint` de modos y esfuerzos.
- Documentación (`README.md`, `docs/architecture/`).
- Prompts que recibe el agente: se dejan en inglés a propósito (ver `traduccion-inventario.md`).
